# M8.1 — Implementation Spec (LLVM Toolchain Bring-Up)

**Status:** working draft — the ordered work plan for **M8 phase 8.1**, expanded into its own
spec because it is large and mostly build/interop plumbing (the real risk of M8). Derived from
`m8-spec.md` (parent — 8.1 and the 8.0.4 decisions), `compiler.md` §2/§6, the Swift.org
**C++ interoperability** guide, and the **`swiftlang/swift-llvm-bindings`** repo. Pins the
bring-up sequence; supersedes the parent's 8.1 slice list. Status tags: **Decided**,
**Leaning**, **Open**.

> Authoring conventions per `lang-project/milestone-doc-guide.md`.

**Build status (2026-07-31):** **not started.** Both forks now **Decided (2026-07-31)**:
**A · adopt `swift-llvm-bindings`** (the official Swift/C++-interop LLVM bindings) as the primary
API, with a thin local supplement only for gaps; **B · bring LLVM in via the official
`llvm/llvm-project` Bazel overlay** (`http_archive` at a pinned commit → `cc_library` targets;
`toolchains_llvm` was rejected — it exposes no libLLVM). Remaining sub-decisions
(unidirectional interop, opaque-handle ownership, no exceptions across the boundary) are the
bindings' concern, inherited.

**Framing:** 8.1 does **almost no language lowering** — its job is to answer "can Swift drive
LLVM through a binding, produce a native binary, inside our bazel build?" for one trivial
program. Everything hard about M8 (full lowering, DWARF, statepoints) waits on this working.
Expanded to its own spec because the interop + LLVM-in-bazel plumbing is the milestone's real
unknown, and it has genuine forks.

**The governing interop fact (Swift.org C++ interop guide):** Swift **cannot import LLVM's raw
C++** — templated APIs (`IRBuilder<>`), the **virtual `Value` class hierarchy**, `std::` types
in signatures, and **C++ exceptions across the boundary** are all unsupported or unsafe. So
*whatever* binding strategy we pick (8.1.0.4-A), the **Swift-facing surface must be flat and
importable**: free functions, opaque pointers, POD structs, scoped enums, `Int`. This is the
load-bearing constraint of the whole phase.

**Prerequisites** (grounded against the repo):
- **M8 decisions** (`m8-spec.md` 8.0.4): drive LLVM's C++ API behind a thin C++ boundary;
  GC roots via statepoints (not this phase); LLVM-only, minimal-correct.
- **Build**: bazel with **`rules_swift` 3.4.2**, **`rules_rust` 0.72.0** (`MODULE.bazel`); the
  compiler is Swift-hosted; the C backend (`src/codegen`) stays as the **differential oracle**;
  runtime is `src/runtime/{runtime,core}.c`.
- **Swift 6.0+ toolchain — satisfied.** Mature C++ interop and `swift-llvm-bindings` require
  Swift ≥ 6.0; Swift 6 has shipped for years, so this is a non-issue, not a gate.

## 8.1.0 · Front matter

### 8.1.0.1 · Scope

**Ships in 8.1:**
- **LLVM in the bazel build** via the `llvm/llvm-project` Bazel overlay (`http_archive` at a
  pinned commit → `llvm_configure` → `@llvm-project//llvm:Core` … `cc_library` targets), built
  from source and hermetic.
- **`swift-llvm-bindings` vendored + built in bazel** (rules_swift, cxx-interop) against that
  LLVM; our compiler imports its Swift modules.
- **A minimal use of the bindings' IR API** sufficient for one program: module/function/
  basic-block, integer constants + add, a call to an external `print`, `ret`, verification.
- A **thin local supplement** only if the bindings lack an API 8.1 needs (e.g. object emission).
- **Object emission + linking**: host-triple `TargetMachine` → `.o`; runtime `→ .a`; link to a
  native binary.
- A **`--backend=c|llvm`** driver selector (C stays default until 8.2 parity).
- The **differential-harness seed** (compare `llvm` vs `c` stdout on the hello-world).

**Deferred** (design ref):
- Full language lowering → `m8-spec.md` 8.2; DWARF → 8.3; statepoints/GC seams → 8.4; perf → 8.5.
- Adopting `swift-llvm-bindings` wholesale — kept as a **future option**, not this phase
  (8.1.0.4-A).

### 8.1.0.2 · Compiler surface touched

- **New build components** — the **`llvm-project` overlay** in `MODULE.bazel` (`http_archive`
  `llvm-raw` + `llvm_configure` + transitive deps); **vendored `swift-llvm-bindings`** as
  `rules_swift` targets (cxx-interop enabled, `-cxx-interoperability-mode=default`) linking the
  `@llvm-project//llvm` targets; an optional `src/llvmgen` supplement for gaps.
- **Driver** — a `--backend=c|llvm` switch; the LLVM path is a sibling of `CodegenIR`, fed by
  the same typed IR, importing the bindings' modules.
- **No frontend/IR change** — 8.1 consumes the existing typed IR unchanged.

### 8.1.0.3 · Dependencies

```
8.1.1 (LLVM in the bazel build)
└─ 8.1.2 (the Swift↔LLVM binding layer: shim + module map + interop mode)
   └─ 8.1.3 (minimal IR-builder surface for hello-world)
      └─ 8.1.4 (object emission + runtime .a + link + --backend selector)
         └─ 8.1.5 (hello-world end to end + differential seed)
(8.1.0-spike · textual .ll → llc)   [optional, throwaway; only if 8.1.2/8.1.3 stall]
```
Strictly linear — each phase is a prerequisite for the next; 8.1 is a pipe that must connect
end to end before it means anything.

### 8.1.0.4 · Big design decisions

- **A · Adopt `swift-llvm-bindings` — Decided (2026-07-31).** Use the official Swift-project
  bindings (Swift/C++ interop **directly** to LLVM's C++ API) as the **primary** IR-building
  API, rather than hand-writing a shim. Rationale: least bespoke C++, rides the Swift team's
  interop work, the blessed path — and, despite a "work-in-progress" README, the repo is
  **actively maintained** (last push 2026-07-15; not archived; default branch `llvm.org/main`
  tracks LLVM upstream). That README caveat is ~4 years stale, not a health signal. **Accepted
  risks + mitigations:**
  - *API coverage (the real residual risk).* Active maintenance ≠ full coverage; the bindings
    may not surface everything we need (`TargetMachine` + object emission now; `DIBuilder` in
    8.3; statepoints in 8.4). Mitigation: **audit coverage early** (8.1.2) and where missing add
    a **thin local supplement** (a small `.cpp`/interop header) and/or **contribute upstream**.
  - *Churn from tracking LLVM main.* The default branch moves with LLVM; **pin a
    `stable/YYYYMMDD` branch or commit + the matching LLVM version** (fork B) so bumps are
    deliberate.
  - *SwiftPM/CMake, not bazel.* We **vendor** the bindings and build with `rules_swift`
    (cxx-interop) against the fork-B LLVM, bypassing their CMake. (Swift ≥ 6.0 is satisfied —
    Swift 6 has shipped for years.)
  - The flat-surface / ownership / exception concerns are now **the bindings'
    responsibility** — we inherit their interop model rather than designing our own.

- **B · LLVM via the official `llvm/llvm-project` Bazel overlay (`utils/bazel`), built from
  source at a pinned commit — Decided (2026-08-01; supersedes the 2026-07-31 `toolchains_llvm`
  pick).** `toolchains_llvm` was rejected on inspection: it's a *compiler toolchain*, not a
  source of libLLVM — it "does not expose LLVM's development libraries as cc_library targets"
  (its own docs; verified). The **LLVM overlay** does exactly what we need:
  - Consumed downstream via **`http_archive` at a pinned `LLVM_COMMIT`** (no git clone / no
    submodule — there's an `http_archive` example), then **`llvm_configure(name =
    "llvm-project")`** generates real `cc_library` targets: `@llvm-project//llvm:Core`,
    `:Support`, `:Target`, `:MC`, `:CodeGen`, etc.
  - **bzlmod-native** (`utils/bazel/{MODULE.bazel,extensions.bzl,configure.bzl}`); macOS
    supported (pulls `apple_support`).
  - **Resolves the A↔B coupling:** we pin `llvm-raw` to the **exact commit `swift-llvm-bindings`
    builds against**, so our backend *and* the bindings link one identical hermetic LLVM.
  - *Costs:* builds LLVM **from source** (heavy first build; cacheable / remote-cache-friendly);
    LLVM's Bazel build is **experimental / best-effort / peripheral-tier**, so pin a known-good
    commit; downstream wiring must supply transitive deps (`zlib-ng`→`llvm_zlib`,
    `zstd`→`llvm_zstd`, `apple_support`, `pyyaml`).

- **C · Interop direction: unidirectional — Decided.** Our compiler (Swift) imports the
  bindings' Swift modules and calls *into* LLVM; nothing calls back into our Swift. No reverse
  interop / `-Swift.h` path.

- **D–E · Ownership + errors — inherited from the bindings.** The bindings define how LLVM
  objects are owned (value vs. reference mapping) and how failures surface; we adopt their model.
  Watch item: confirm their surface never lets a C++ exception cross to Swift (interop
  requirement) and that object emission / verify failures are returned, not aborted (8.1.2).

### 8.1.0.5 · Runtime posture + where LLVM lives

**One LLVM integration, into the compiler.** LLVM is a *compile-time* dependency of **`nomuc`**
only: `nomuc` → our codegen ("the backend") → `swift-llvm-bindings` → libLLVM, all one binary
with **one statically-linked libLLVM**. The "backend" and "the bindings" are the same program,
not two consumers. **Compiled Nomu programs ship no LLVM** — a program is native code + the Nomu
runtime `.a` + libc (LLVM produced it, like clang produces a C binary, but isn't in it).
Consequence: `nomuc` becomes a large binary (libLLVM is hundreds of MB — normal for a compiler);
a packaging concern for the M8 tail, not 8.1. Programs stay small.

The alloc seam stays `rt_alloc`. Runtime `.c` compiles to a `.a` and links into *target
programs* (8.1.4) — the `compiler.md` §6 "preamble → runtime library" item, now real for the
LLVM path (not linked into `nomuc` itself; `nomuc` embeds the runtime *source* to emit).
`ucontext`, fiber-aware mutex, and other runtime evolutions are **not** in 8.1 (perf tail,
`m8-spec.md` 8.5).

### 8.1.0.6 · Risks / watch items

- **`swift-llvm-bindings` API coverage (highest, the A-decision's cost).** The repo is actively
  maintained (last push 2026-07-15; the "WIP" README is ~4yr stale), so abandonment is *not* the
  worry — **coverage** is: it may not surface `TargetMachine`/object emission (8.1.4),
  `DIBuilder` (8.3), or statepoints (8.4). Mitigation: **audit coverage early** (8.1.2); fill
  gaps with a thin local supplement or upstream contribution. Pin a `stable/YYYYMMDD` branch +
  matching LLVM to keep churn deliberate.
- **Vendoring a SwiftPM/CMake package into bazel.** The bindings ship CMake/SwiftPM; we
  hand-wire `rules_swift` targets against the LLVM `cc_library`, bypassing their build. Real
  integration work in 8.1.2; watch for hidden build assumptions (generated headers, LLVM_DIR).
- **rules_swift 3.4.2 cxx-interop enablement.** Confirm 3.4.2 wires
  `-cxx-interoperability-mode=default` cleanly for the bindings' targets — a config step, low
  risk (Swift 6 itself is a settled non-issue).
- **LLVM overlay: heavy from-source build + experimental tier.** `@llvm-project` builds LLVM
  from source (long first build; mitigate with build/remote cache) and LLVM tags its Bazel build
  experimental/best-effort — **pin a known-good commit**; bumps are deliberate. Downstream
  wiring must supply transitive deps (`llvm_zlib`/`llvm_zstd`/`apple_support`/`pyyaml`).
- **ABI / build-config match** — the LLVM libs (built by the overlay), our C++ code, and the
  bindings' interop layer must share a C++ ABI (libc++ / exceptions / RTTI). On macOS the system
  libc++ + the Swift toolchain's clang give consistency; watch RTTI/`-fno-exceptions` flags on
  the overlay vs. consumers.

## 8.1.1 · LLVM in the bazel build (llvm-project overlay) ✅ built + green (2026-08-01)

Intent: a pinned, hermetic LLVM exposed as linkable `cc_library` targets, proven from C++ before
any Swift is involved. Deps: none. Approach (8.1.0.4-B): the `llvm/llvm-project` Bazel overlay
via `http_archive` at a pinned commit + `llvm_configure`.

- 🔨 pinned to **LLVM 23** (decided 2026-08-01: start latest, fall back to 21.x only on
  trouble — major-version bumps are involved, so begin current). `LLVM_COMMIT` =
  `af6b25907abe4bf391dc17d3d1106cc58a0252b6` (`release/23.x` @ 2026-07-31; `llvmorg-23.1.0-rc2`
  era). Bindings pair: `stable/23.x`. Both vanilla upstream, so they match.
- ✅ `MODULE.bazel` wiring — **analysis green (2026-08-01).** `@llvm-project` configures and the
  smoke target analyzes (4552 targets). Key learnings:
  - `@llvm-raw` (pinned llvm-project tarball) + `pyyaml` are created in a **local module
    extension** (`bazel/llvm_extensions.bzl`) and exposed via `use_repo` — a `use_repo_rule`
    repo isn't visible as a `.bzl` source in the same module, so `llvm_configure` couldn't load
    from it otherwise (mirrors the overlay's own `extensions.bzl`).
  - Transitive `bazel_dep`s the generated `@llvm-project` needs: `rules_cc`, `platforms`,
    `bazel_skylib`, `rules_python`, `rules_shell`, **`llvm` 0.8.5** (`@llvm//platforms/config`),
    `zlib-ng`→`llvm_zlib`, `zstd`→`llvm_zstd`, `apple_support`→`build_bazel_apple_support`.
  - Digest pinned: `integrity = "sha256-BRccRYlAeIfQHCTA+i9PViwOP6UrX8MoYeVO0o/zjyI="`.
  - Bazel 9 removed builtin `cc_binary` → `load("@rules_cc//cc:defs.bzl", "cc_binary")`.
  - **Toolchain regression + fix:** adding `rules_cc` + the overlay perturbed C++ toolchain
    resolution, so rules_swift saw the autodetected `local` CC toolchain ("Invalid target
    triple: local") instead of Apple's. Fixed by registering apple_support's toolchain from the
    **root** module (`use_extension` `apple_cc_configure_extension` + `use_repo` +
    `register_toolchains("@local_config_apple_cc_toolchains//:all")`). Existing
    `//src/...` build + both test suites stay green.
- ✅ `src/llvmgen/llvm_smoke.cpp` (`@llvm-project//llvm:Core` + `:Support`) builds a tiny
  `Module` (`answer() -> i64 { ret 42 }`), verifies, prints IR. **`bazel run` → valid IR,
  exit 0.** First from-source LLVM compile: **~43s / 809 actions** (only Core+Support+deps, not
  all of LLVM — far cheaper than feared; cached thereafter).

**Exit — met.** `bazel run //src/llvmgen:llvm_smoke` builds an `LLVMContext` + `Module` and
prints valid IR (`define i64 @answer() { ret i64 42 }`), exit 0; `llvm-raw` pinned at
`af6b259` + digest; the overlay build is green. **8.1.1 complete.** Next: 8.1.2 (vendor
`swift-llvm-bindings` + coverage audit).

## 8.1.2 · Vendor + build `swift-llvm-bindings` in bazel ⬜

Intent: get the official bindings compiling under bazel and importable from our Swift compiler.
Deps: 8.1.1. Approach (8.1.0.4-A): vendor a pinned bindings commit; build with `rules_swift` +
cxx-interop against the 8.1.1 LLVM `cc_library`; bypass their CMake.

- ⬜ vendor `swift-llvm-bindings` at a pinned `stable/*` branch/commit; hand-write `rules_swift`
  `BUILD` targets for its modules, linking the LLVM `cc_library`, with
  `-cxx-interoperability-mode=default` on.
- ⬜ round-trip: our compiler `import`s a bindings module, builds a trivial `Module`, prints its
  IR / verifies it.
- ⬜ **coverage audit (the phase's real unknown):** map the bindings' API against 8.1.4 (object

**Exit:** our Swift compiler imports `swift-llvm-bindings` and, through it, builds and verifies a
trivial LLVM module; the vendored bindings build under bazel at a pinned commit; the
**coverage-gap list** exists and sizes the supplement.

## 8.1.3 · Minimal IR building for hello-world ⬜

Intent: express `main` through the bindings' API (plus supplement if needed). Deps: 8.1.2.
Approach: use the bindings' module/function/builder API; add a thin supplement only for a missing
call.

- ⬜ build, via the bindings: module + `main`; `i64` constants; `add`; declare + `call` an
  external `print`/`printf`; `ret`; verify the module.
- ⬜ if any needed op is uncovered, add the **thin local supplement** (interop header/`.cpp`) and
  record it.

**Exit:** an arithmetic-`main` that calls an external print is built and verified entirely from
Swift via the bindings (+ any recorded supplement).

## 8.1.4 · Object emission + runtime .a + link + backend selector ⬜

Intent: turn IR into a running native binary. Deps: 8.1.3. Approach: `TargetMachine` object
emission (via the bindings or a supplement); runtime → `.a`; link; a driver switch.

- ⬜ host-triple `TargetMachine` → object file (bindings API, or supplement if uncovered — a
  a likely coverage gap).
- ⬜ compile `runtime.c` + `core.c` to a static `.a`; link generated `.o` + runtime `.a` → a
  native binary (replaces the C backend's per-file `cc` co-compile for this path).
- ⬜ driver `--backend=c|llvm` (default `c`); the `llvm` path routes typed IR → bindings → object
  → link.

**Exit:** the LLVM path emits an object, links it with the runtime `.a`, and produces a native
executable; `--backend=llvm` is wired in the driver.

## 8.1.5 · Hello-world end to end + differential seed ⬜

Intent: the phase's payoff — one real Nomu program through the whole LLVM path, checked against
the C backend. Deps: 8.1.4. Approach: lower a trivial `main` from the typed IR; seed the
differential harness `m8-spec.md` 8.2 will grow.

- ⬜ lower `fun main` with integer arithmetic + `print` from the typed IR via the bindings (a
  first sliver of 8.2's 8.2.1, only what hello-world needs).
- ⬜ differential-harness seed: build the program with both backends, assert identical stdout +
  exit.

**Exit:** `fun main { print(2 + 3) }` (or similar) compiled with `--backend=llvm` runs natively
and prints the same as `--backend=c`; the differential seed passes and is ready for 8.2 to
extend. **M8.1 done** — the toolchain pipe connects end to end.
