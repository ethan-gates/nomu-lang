# M4.10 — Implementation Spec (M5 prerequisites: enum construction + `let` fields)

**Status:** DONE (2026-07-23). A short prerequisite slice between M4.9 and M5, carved out the same way M4.9 was. Both items (E1 enum construction — qualified + leading-dot; E2 `let` fields) shipped and are green; the syntax checkpoints in §4 were decided (both construction forms, labeled payload). Exit criteria met — see `examples/enums.nomu`. Found by grounding M5's exit criteria against the code (the M5 prerequisite audit): two of M5's headline deliverables can't run on the current compiler for reasons that are **not** generics/interfaces work.

**Why it exists.** M5 Phase B builds `Option<T>` and `Box<T>`; Phase E builds `Result<T, E>`. Grounding those against the code:

- **Enum values cannot be constructed.** `Sema.checkCall` constructs `struct`/`class`/`actor` only (`if let k = kindOf(name), k != .enum_`); there is no `.case(...)` / `Type.case(...)` path, and a leading `.` does not parse as an expression. Enums today are **match-only** — no example ever constructs one. `Option<T>` and `Result<T, E>` are enums whose purpose is being constructed and returned, so the generic versions have nothing to build on until concrete enum construction exists.
- **`let` fields do not exist.** Type bodies accept only `var` fields (`parseVarField` hard-requires `.kwVar`). `Box<T> { let value: T }` (Phase B exit) uses a `let` field, and Phase C's "a deeply-immutable class (all `let` fields, recursively) is shareable" needs field-level immutability — the model in `memory-model.md` §4 that the compiler hasn't built.

Both are small, concrete, non-generic features — the **M4.9 pattern** (build the concrete feature; M5 layers generics/interfaces on top). Doing them now avoids discovering them mid-Phase-B when `Option<T>` won't run.

---

## 1. Scope

**Ships in M4.10:**
- **Concrete enum value construction** — create an enum value naming a case and its payload, type-checked against the case's declared fields, lowering to the tagged-union literal codegen already knows the shape of.
- **`let` fields on `struct`/`class`** — field-level immutability. The mutability is threaded AST → typed IR (`IRField`) so M5 Phase C's deeply-immutable-class check can read it. Assigning to a `let` field is a collected diagnostic.

**Deferred (stays M5):**
- **Generic** enum construction (`Option.some(x)`) and generic `let` fields — Phase B, on top of this.
- **Mutating methods / property setters** on value types (`var self` write-back) — Phase A.
- **Overload resolution / symbol-table rework** (tables are `[String: X]`, name-keyed) — M5 §4.2.
- **Loops + collections** — post-M5 (roadmap); see §5 for the Phase A demo consequence.

---

## 2. Pipeline touched

- **Lexer** — no new keywords: `let` already exists; enum construction reuses `.` / identifiers.
- **AST / Parser** — parse enum construction as an expression; `VarField` gains a mutability flag; type bodies accept `let` fields (same line-start rule as `var`, `syntax.md` §2).
- **Sema / IR** — resolve enum construction to a typed IR node (a new `ExprKind`, e.g. `enumInit`, or an extension of `construct`); thread field mutability onto `IRField`.
- **Typechecker** (POD + let/var) — reject assignment to `let` fields; POD applies to `let` fields unchanged.
- **Codegen** — emit the enum tag + payload literal for construction; `let` fields need no special C.

---

## 3. Items

### E1 — Concrete enum construction
Parse and type an enum-construction expression; lower to an IR node naming the enum, the case, and the typed payload args; codegen sets `.tag = Enum_case` and fills `.payload.case = { … }`.
- **Exit:** an enum value is constructed, passed to a function, and `switch`ed on; it round-trips at runtime.

### E2 — `let` fields
`let name: T` in a type body, parsed like `var` (line-start rule applies), carrying immutability into `IRField`. Assigning to a `let` field (bare name, or `self.field =` / `value.field =`) is a clean collected diagnostic.
- **Exit:** a struct/class with a `let` field compiles and reads; assignment to it is a collected diagnostic; the immutability is visible on `IRField` (for M5-C).

## 4. Syntax checkpoints (confirm before parser work — `CLAUDE.md`)

- **Enum construction surface — DECIDED (2026-07-23): both forms.**
  - **Qualified** `Shape.circle(radius: 1)` — the enum type is named at the site; already parses today (a call on a member access), so Sema + codegen only.
  - **Leading-dot** `.circle(radius: 1)` — sugar; the expected enum type is inferred from context (binding annotation, call-argument position, return position). Matches the pattern spelling `case .circle(let r)`. Needs a new `implicitMember` AST node + **contextual (expected-type) inference** threaded through the checker — a scoped addition to the modest bottom-up inference (nil expected → `.case` is a clean "cannot infer enum type" error).
  - Payload is **labeled** at construction (`radius: 1`), matching struct construction. No-payload cases construct bare (`Color.red`, `.red`).
- **`let` fields** reuse the existing `let` keyword in a new position (no new keyword). Confirm the surface — each field on its own line, e.g.

  ```
  struct P {
      let x: Int
      var y: Int
  }
  ```

## 5. Consequence for M5 Phase A (the iteration demo)

M5 Phase A's exit criterion iterates a `[any Drawable]`, but the language has **no loops and no collection type** today (and real generic collections depend on M5 generics). Resolve by either demonstrating `any` dispatch on individual `any Drawable` values (no collection), or pulling minimal iteration forward. This is a decision to record in `m5-spec.md` — not M4.10 build work.
